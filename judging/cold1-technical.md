## Scores

**(a) Quality of the idea — 7/10.** The problem is real and well-scoped for CA-14 (multilingual civic access), but "AI multilingual summarizer" is a familiar archetype, not an invention. What elevates it above the archetype is the verifiability loop as the product: every claim cited to (file, page), citations clickable to exact source text via `/api/chunk`, an eval harness scoring citation validity/grounding/advisory-language, and an honesty architecture (mock mode refuses to fabricate summaries; golden examples labeled hand-verified). RAG-with-citations is a known pattern; the discipline around it is the contribution. Above average, not groundbreaking.

**(b) Implementation — 7/10.** The app boots clean, serves 5 featured cards with real non-English script (verified Hindi/Chinese live), citation drill-down returns exact source text, error paths return JSON (400s/404s, path-traversal blocked), and the demo-mode footer is legible. Docked because the core interactive promise — "ask anything, get a cited summary" — cannot be demonstrated without an LLM key the project doesn't have: in mock mode `/api/ask` returns sources plus "live summaries need an LLM key." As a demo it is coherent and persuasive; as a general tool it is currently a curated prototype. The 90-second demo path (language → card → cited claims → verify) is fully functional.

**(c) Demonstrated excellence of coding — 8/10.** This is genuinely well-engineered code that survives expert reading. Highlights verified: parser.py does real two-column reading-order recovery and statistical header/footer stripping; retriever.py has a sha256-pinned source manifest that empirically rejects unlisted files; eval.py is unicode-aware (Devanagari/Gurmukhi/CJK bigrams/Perso-Arabic) with an explicitly documented cross-lingual policy; the metadata boost (+0.15 bounded keyword overlap on section titles/filenames) is a principled, documented hybrid fix for a real failure mode embeddings miss; error handling is defensive throughout (human-readable messages, never raw tracebacks); limitations are disclosed in-code (advisory.py's COVERAGE HONESTY header is exemplary). Docked one point: the load-bearing path — real LLM output through summarize→evaluate — has zero test coverage. The harness is proven on its own mechanics and on hand-written claims, never on actual model output.

## Verified findings (ranked by lethality)

1. **No real LLM has ever run through the pipeline. (VERIFIED — most load-bearing gap.)** MockLLM emits generic English placeholders; the golden set is hand-written. The eval harness therefore validates its own mechanics + hand-written claims, never real model output. Citation validity, advisory detection, and English grounding are real; the end-to-end AI behavior is unproven. Partially mitigated: EVAL_REPORT.md discloses this explicitly, and the architecture is key-ready (env-var config, three transport fallbacks). A single real-key run before submission would close most of this.
2. **Non-English grounding is via English shadow text. (VERIFIED.)** Golden claims carry no `claim_en`; gen_eval_log.py synthesizes it from the English text, so Hindi/Punjabi/Chinese/Farsi claims are scored on their English equivalent. The method string in eval_log.json discloses this ("proves the CONTENT is in the source, not that the translation is faithful"). Translation faithfulness itself is untested — no bilingual review, no MT-quality metric. The non-English text IS advisory-scanned (real check), just not grounding-scored.
3. **Advisory detection is substring matching; paraphrases evade it. (VERIFIED empirically.)** "You might consider supporting this measure" passes silently. This is a keyword backstop, not a safety property — though it is honestly disclosed in advisory.py and the prompt also bans advisory phrasing (defense in depth, both layers have the same ceiling).
4. **Retrieval is good, not great. (VERIFIED.)** 9/9 golden tests pass on 1,238 chunks, but as top-5 assertions, not rank-1; top scores run 0.5–0.7 and the corpus is English-only, so non-English query retrieval is untested. The metadata boost is principled but simple. Adequate for the demo; not a retrieval research contribution.
5. **Minor:** EVAL_REPORT.md's §5 was written against the 903-chunk corpus; the log has since been regenerated at 1,238 — doc/code drift of this kind should be re-checked before submission. (Fixed during this review for README/SUBMISSION chunk counts; the report text itself still references older numbers in one section.)

**Not flaws (checked, held up):** manifest guard rejects planted fixtures; all 10 spot-checked citations resolve to real supporting chunks; no API keys anywhere in the repo; requirements pinned and installable; `/api/chunk` traversal-proof; mock mode never fabricates summaries; golden translations are real script saying real things with real citations.

## Verdict: YES

This clears the bar for CA-14 on technical merit. My skeptic's brief was "prompt chain or engineering" — the answer is engineering: a real retrieval pipeline with a working integrity guard, a real (if bounded) eval harness, and defensive, well-tested code throughout. The remaining gaps are disclosed limitations, not hidden failures, and the single highest-value step before submission (one real-key run through summarize→evaluate, logged) is environmental, not architectural. A careful judge reading this code would find it sound.
